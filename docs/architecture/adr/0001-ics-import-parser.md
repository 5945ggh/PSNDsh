# ADR 0001: 以受限窗口导入 ICS 日程

- 状态：Accepted
- 日期：2026-07-22

## 背景

日历已经可以持久化单个日程，但现有 `schedule_blocks.recurrence_json` 只能表达简单的每周规则，不能无损保存 RFC 5545 的 `EXDATE`、`RECURRENCE-ID`、全天语义或原始时区。前端已有“选择文件 -> 预览 -> 确认”的交互，不能让其在持久化模式中假装成功。

## 决定

首版服务端使用精确锁定的 `node-ical@0.26.1`（Apache-2.0），且只通过 `ical.async.parseICS()` 解析用户提供的文本，不从 URL 拉取文件。解析器只在 Node.js route handler 侧使用。

导入采用受限的具体实例展开，而非把不完整的 recurrence DTO 写入数据库：

- 单次定时事件直接导入。
- 带明确 `TZID` 或 UTC `Z` 时间的重复事件在“当前时刻起 180 天”窗口内展开为具体 `schedule_blocks`；未声明时区的重复事件也在同一窗口展开并映射到 `effectiveTimezone`。`node-ical` 负责 IANA 时区、DST、`EXDATE` 和 `RECURRENCE-ID` 覆盖。
- 每个预览最多接收 200 个 VEVENT、1,000 个展开实例；超过上限会在预览中拒绝，避免无限 RRULE 或大文件阻塞服务。
- 文件大小上限为 1 MiB；预览仅在内存保存 15 分钟，按用户与随机 import ID 隔离，确认后一次性消费。进程重启会使预览失效。
- 全天事件、无结束时间或无效时间范围会逐条出现在预览的过滤说明中，不写入数据库。
- 不带时区的单次和重复定时事件都按照实例 `effectiveTimezone` 解释。重复事件先由 parser 展开，再把墙上时间映射到应用时区，避免宿主默认时区改变语义；预览会明确提示这一解释方式。
- 每次确认写入都会建立一个导入批次；已有相同 `sourceUid` 的候选默认跳过，服务端确认时再次去重。用户可以删除批次及其全部具体实例。

确认接口只接收预览返回的 source UID，服务端从预览存储中取回规范化候选项并以当前会话用户写入；客户端永远不能提交任意日程对象。

## 后果

该方案让当前周历直接显示具体实例，同时在导入窗口内保留异常日期、覆盖和 DST 的实际结果。代价是无限重复不会在窗口之外自动延续，且初版不支持全天事件。后续如需无期限课程同步，应增加保存 RFC 5545 源元数据、原始 TZID、例外日期与覆盖的迁移，而不能仅扩展现有 weekly DTO。

同一文件再次上传不会重复写入已有 `sourceUid`，但也不会更新既有实例或处理源端删除；需要替换整份课表时，先在日历页删除旧导入批次，再确认新文件。

## 备选方案

- 扩展 `schedule_blocks` 以原样保存完整 RFC 5545：保真度更高，但需要日历投影、迁移和编辑语义一起重新设计，超出当前渐进批次。
- 只接受简单 weekly RRULE 并静默忽略例外：拒绝，因为会产生错误的课程表。
- `ical.js`：成熟但需要额外的时区注册/数据工作，且 MPL-2.0 的合规边界更复杂。
- `ical-expander`：维护与同步展开风险不如 `node-ical` 可控。

## 验证

解析 fixture 覆盖 IANA TZID 的 DST、`UNTIL`、`EXDATE`、`RECURRENCE-ID`、无时区单次和重复事件；服务与浏览器测试覆盖用户隔离、确认一次性消费、重复来源保护、批次删除以及日历持久化显示。
